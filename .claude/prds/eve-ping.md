# PRD: eve-ping

## Executive Summary

`EvePing-for-Discord` は、Discordの Scheduled Event（予定されたイベント）の開始前日に、そのイベントに「興味あり (Interested)」を表明したユーザーへ個別DMでリマインドを送るBotである。姉妹プロジェクト `7DaysPoll-for-Discord`（投票で日程を決めるBot）から「イベント前日リマインド」機能をスコープ外として切り出したスピンオフ企画であり、DB・KVストアを持たないステートレスな軽量構成を踏襲する。

## Problem Statement

Discordのscheduled eventには開始直前の自動通知はあるが、「前日」というリードタイムで個別にリマインドする機能はない。イベント参加者が前日に予定を思い出し、都合を調整したり忘れずに参加したりするための仕組みがなく、これは7DaysPollのミッション（投票で日程を決めるまで）の範囲外である。決定後のイベント運営に関するこのニーズに応える専用のシンプルなBotが必要。

なぜ今か: 7DaysPollのユーザーから直接この要望が上がっており、既存プロジェクトの設計原則（投票期間中のみ生きるin-memory状態）と相容れないため、別プロジェクトとして独立させることで両方のシンプルさを保てる。

## User Stories

### US-1: イベント前日にリマインドを受け取る
**As a** Discordサーバーのメンバーで、あるscheduled eventに「興味あり」を押した人
**I want** イベント開始の前日に個別DMでリマインドを受け取りたい
**So that** 予定を忘れずに、必要な準備や調整ができる

**受け入れ基準:**
- イベント開始日の前日（UTC基準）に、Botからそのユーザー宛に個別DMが届く
- DMにはイベント名・開始日時・（可能であれば）イベントへのリンクが含まれる
- CANCELED または COMPLETED ステータスのイベントについてはリマインドが送られない
- 「興味あり」を押していないユーザーにはDMが届かない

### US-2: サーバー管理者として、設定なしでBotを導入したい
**As a** Discordサーバーの管理者
**I want** Botを招待するだけで、チャンネル設定や有効化の作業なしにリマインド機能が動き出してほしい
**So that** 導入・運用の手間をゼロにできる

**受け入れ基準:**
- Botをサーバーに招待した時点で、追加設定なしにそのサーバーのscheduled eventsが監視対象になる
- サーバー側の設定を保存するデータストアが存在しない

### US-3: DM送信に失敗しても他のユーザーへの通知が止まらない
**As a** システムの運用者
**I want** 一部のユーザーへのDM送信が失敗しても（DM拒否設定など）、バッチ処理全体が止まらずに他のユーザーへの送信が継続してほしい
**So that** 一人の設定によって全員のリマインドが失われる事態を避けられる

**受け入れ基準:**
- あるユーザーへのDM送信がエラー（例: エラーコード50007 = DM拒否）になっても、後続ユーザーへの送信処理が継続する
- 送信失敗はログに記録される（再送はしない）

## Functional Requirements

### FR-1: 全ギルド走査
Botが導入されている全ギルドをdiscordgoのセッションstateから取得する。

### FR-2: Scheduled Events取得とフィルタリング
各ギルドのScheduled Events一覧を取得し、以下の条件で対象イベントを絞り込む。
- 開始日時が「明日」（UTC基準で日付比較）であること
- ステータスが `SCHEDULED` または `ACTIVE` であること（`CANCELED` / `COMPLETED` は除外）

### FR-3: 興味ありユーザー一覧取得（ページネーション対応）
対象イベントごとに「興味あり」ユーザー一覧を取得する。Discord APIは1回最大100件・`before`/`after`カーソルでページネーションされるため、全件取得できるまでループ取得する。

### FR-4: 個別DM送信
対象イベント × 対象ユーザーの組み合わせごとに、個別DMチャンネルを開いてリマインドメッセージを送信する。メッセージにはイベント名・開始日時・イベントへのリンクを含める。

### FR-5: 送信失敗のハンドリング
DM送信（DMチャンネルのオープン含む）が失敗した場合、そのユーザーの失敗をログに記録し、処理を継続する（他のユーザー・他のイベントへの送信は止めない）。再送は行わない。

### FR-6: 日次バッチ実行
Botプロセス内で1日1回、上記FR-1〜FR-5のバッチ処理を実行する。実行時刻はUTC基準で固定する（具体的な時刻は実装時に決定）。

## Non-Functional Requirements

### 永続化なし
DB・KVストアを一切使用しない。全ての状態はDiscord APIから毎回取得し、プロセス内メモリのみで完結する。プロセス再起動によって状態が失われても機能に支障がないこと。

### ステートレス設計
ギルド単位・チャンネル単位の設定を一切保持しない。Botトークンのみで動作する。

### 可用性
Botは常駐プロセスとして継続稼働する（7DaysPollと同様の構成）。プロセスが停止していた期間のバッチは実行されない（キューイングやリカバリは行わない）。

### 障害の局所化
1件のDM送信失敗・1ギルドのAPI取得失敗が、他のギルド・他のユーザーへの処理に波及しないこと。

### ログ可観測性
バッチの開始・終了、処理対象イベント数、送信成功数・失敗数がログに出力されること。

## Success Criteria

- 前日リマインド対象イベント（SCHEDULED/ACTIVEかつ開始日が翌日UTC）に対し、興味ありユーザーの100%にDM送信が試行される（DM拒否等の個別失敗は成功率に含めない）
- CANCELED/COMPLETEDイベントに対する誤送信が0件であること
- 100件を超える興味ありユーザーを持つイベントで、ページネーション漏れによる送信対象漏れが0件であること
- 1ユーザーへの送信失敗が原因で他ユーザー・他イベントへの送信が中断された事例が0件であること
- 外部DB・KVストアへの依存なしに1週間以上安定稼働できること

## Constraints & Assumptions

- **実行環境**: 常駐プロセス + `time.Ticker`（7DaysPollと同様の構成）。外部cronや単発実行バイナリは採用しない。
- **タイムゾーン**: 「明日」判定はUTC固定とする。ギルドごとのタイムゾーン設定は考慮しない。
- **二重送信対策**: v1では対策を実装しない。プロセス再起動によって同一イベントへの重複DMが発生するリスクは許容する（永続化なしのシンプルな構成を優先するトレードオフ）。
- **技術スタック**: Go + discordgo（7DaysPollのGo構成を流用できる想定）。
- **権限**: Botには対象ギルドでDM送信に必要な権限・Intentが付与されている前提。ユーザー側のDM拒否設定は制御不可能な外部要因として扱う。

## Out of Scope

- 投票やスケジュール決定機能（7DaysPollの責務）
- チャンネルへのメンション通知（個別DM以外の通知手段）
- リマインドタイミングのカスタマイズ（前日以外のタイミング、複数回リマインドなど）
- ギルドごとのタイムゾーン設定・カスタマイズ
- 送信済みイベントの永続化による二重送信の完全防止
- DM送信失敗時の再送・リトライ機構
- 管理者向けのダッシュボードや設定UI
- イベント作成・編集・削除などのイベント管理機能

## Dependencies

- Discord API（Scheduled Events API、Guild Scheduled Event Users API、DM送信API）
- discordgoライブラリ（Go向けDiscord APIラッパー）
- Botトークンの発行・Discord Developer Portalでのアプリケーション設定（Botに必要なIntent: `GUILD_SCHEDULED_EVENTS` 等の有効化）
